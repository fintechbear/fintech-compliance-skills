## 2. The real finding: the numbered citations had DRIFTED

The language/DB skills cited refusal rules **by number**, but those numbers no longer
matched `skills/refusal/refusal-policy.md`. Verified current numbering vs. what the files
cited:

| Cited "rule" | File's intended meaning | Correct FCS id | Current policy # |
|---|---|---|---|
| rule 5 | KYC/AML/sanctions screening | FCS-AML-001 | 6 |
| rule 6 | money-movement audit | FCS-AUDIT-001 | 7 |
| rule 10 | least-privilege / access control | FCS-AUTHZ-001 | 11 |
| rule 8 | TLS in transit **or** key mgmt (by line) | FCS-TLS-001 / FCS-SECRET-002 | 9 / 8 |
| rule 1 | PAN storage **vs** CVV **vs** PAN logging (by line) | FCS-PAN-001 / FCS-SAD-001 / FCS-LOG-001 | 1 / 2 / 4 |

So citing by number was already wrong. Every one of the 58 citations was resolved from
**the line's actual context**, not by a 1:1 number remap — e.g. the same old "rule 1" maps
to three different FCS ids depending on whether the line is about storing a PAN, storing a
CVV, or logging a CVV. The full per-line mapping is in `controls/refusal-citation-migration.json`.

## 4. Out of scope / NOT_RUN this phase

- No agent runtime used (P03 is deterministic content + schema work).
- Legal citations in the catalog are **needs_review**: the article numbers are plausible
  placeholders (PCI Req 3.5.1 / 3.3.1, ISO 4217) but were NOT confirmed against primary
  text this phase. `review_status` reflects that honestly; nothing is marked `verified`
  except project-policy and engineering-recommendation claims the project itself owns.
- PCI PAN-vs-CVV distinction preserved: FCS-PAN-001 forbids only readable/logged PAN
  (unreadable-at-rest is allowed); FCS-SAD-001 is the stricter never-store-CVV rule. No
  blanket "never store any PAN" generalization was introduced.
